# أمان صور الملاعب وتخزينها

يدعم التطبيق صور الملاعب فقط؛ لا يوجد رفع لإيصالات الدفع أو اعتماد على R2. يقبل المتصفح ملف JPEG/PNG/WebP أصليًا حتى 10 MiB، يفك الصورة على جهاز المالك، ويعيد ترميز البكسلات على Canvas إلى WebP ثابت منزوعة بيانات EXIF/XMP قبل الإرسال. يقيّد تجهيز المتصفح الأبعاد بـ12 مليون بكسل و1800 بكسل لكل جانب، ويكرر الضغط/التصغير حتى لا يتجاوز الناتج 1,500,000 بايت. لا يرسل الملف الأصلي إلى الخادم.

الخطة المجانية لـWorkers تتيح 10ms CPU فقط لكل طلب، لذلك لا يفك الخادم الصورة ولا يشغّل Photon؛ استهلكت تجربة معالجة Photon المحلية لصورة عالية التفاصيل نحو 2.3 ثانية. بدل ذلك يحدّ Pages Function الطلب إلى 1.5MB ويرفض إلا `Content-Type: image/webp`، ثم يفحص توقيع RIFF/WEBP، الحجم، بنية المقاطع، توقيعات إطار VP8/VP8L، الأبعاد، وغياب مقاطع EXIF/XMP/ICC/الأنيميشن أو المقاطع غير المعروفة. هذا فحص للحاوية والإطار، وليس فكًا برمجيًا كاملًا لبتات البكسل داخل Worker؛ الـWebP النهائي يُنتجه Canvas المتصفح.

لا يثق الخادم في `pitchId` المرسل وحده: يتحقق من جلسة المالك وCSRF والمصدر وحدود المعدل، ثم يثبت أن الملعب نشط ويتبع المكان نفسه. تحفظ الصورة وحدث التدقيق داخل `D1.batch` ذرّي؛ استبدال صورة الملعب يحذف الصورة السابقة فقط إذا نجح إدخال الصورة الجديدة والتدقيق. قيد D1 يفرض `length(image_bytes) = byte_size` وحد 1,500,000 بايت، وصورة نشطة واحدة لكل ملعب. يستخدم ETag عشوائيًا مبنيًا على UUID، ولا يحسب hash لصورة كبيرة على Worker.

يعرض `/api/media/:id` صور WebP فقط بعد التحقق من BLOB والحجم. تظهر الصورة للعامة فقط إذا كان الحجز العام والمِلعب نشطين؛ خلاف ذلك تتطلب جلسة مالك المكان نفسه. لا تعرض API مفتاح تخزين أو بيانات حجز أو إيصالًا. تستخدم الاستجابة `nosniff` و`Cross-Origin-Resource-Policy: same-site`، وCache خاصًا للمعاينة.

## حدود المجانية

الحد الأعلى للصورة الواحدة 1.5MB بعد المعالجة، والملف الأصلي 10MB. قاعدة D1 المجانية محدودة بـ500MB لكل قاعدة وفق وثائق Cloudflare؛ المساحة مشتركة بين الصور والحجوزات والجداول والفهارس، لذا عدد الصور أقل من ناتج قسمة المساحة على حد الصورة. حدود القراءة والكتابة اليومية وCPU المجاني مستقلة أيضًا. عند امتلاء D1 أو انتهاء الحصة، يفشل الحفظ دون نجاح كاذب؛ لا يفعّل المشروع R2 أو خطة مدفوعة تلقائيًا.

## ملاحظة الترحيل

الترحيل `0006_d1_pitch_image_blobs.sql` يعيد إنشاء جدول `media_assets` ليتخلص من أعمدة R2 وبيانات الإيصالات القديمة؛ لا يمكن نقل كائنات R2 إلى D1 لأن بايتاتها لم تكن محفوظة في SQLite. قاعدة المستخدم الحالية معروضة بلا جداول، لذلك يطبق الترحيل قبل بيانات صور حقيقية. إذا نُشر إصدار قديم وخُزنت فيه صور بالفعل، احتفظ بنسخة احتياطية قبل تطبيق الترحيل؛ ستحتاج الصور إلى إعادة رفع بعده.
